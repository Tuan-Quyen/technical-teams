Start a new project with the technical team:

$ARGUMENTS

You are the lead: follow `${CLAUDE_PLUGIN_ROOT}/agents/team-lead.md` §1 and §3–§6 — Read it if you are not already the lead. Empty request → resume from `.team/STATE.md`, or ask for the idea or PRD path. Not a git repo → ask the user to run `git init` first.

0. **Task list** — before the first spawn, put the steps below on the session's task list, one item per step (`update_plan` in the desktop app; `TaskCreate`/`TaskUpdate` in the CLI, loaded via ToolSearch if deferred; else `TodoWrite`), and keep it current (lead §3 *Task list*). No task tool → carry on: `STATE.md` is the truth and the list is rebuilt from it on resume.
1. **Requirements** — `technical-team:team-ba` writes `.team/PRODUCT.md` and the MVP `.team/requirements/<slug>.md`. Show its questions to the user and wait.
2. **Stack + design** — in parallel: `technical-team:team-architect` proposes 2–3 options with one recommended for each stack choice the user left open (a stack the user named is a decision: record it in an ADR), writes `ARCHITECTURE.md` and the ADRs (numbers from the lead); `technical-team:team-designer` (if there is UI) writes `frontend-design/DESIGN.md` and the MVP screen spec `frontend-design/<slug>.md`. Show the user and wait for the stack choice.
3. **Plan** — `technical-team:team-architect` writes `.team/system-design/<slug>.md`; `technical-team:team-pm` writes the tickets in `TASKS.md` grouped by milestone (M1 = walking skeleton: build, lint, test runner, one end-to-end slice). **Workflow opt-in** — the Workflow tool is available (also if deferred) AND the user typed a slash command of this plugin for this item (this command, or `/technical-team:run`, which hands the chosen pipeline to the lead) → run the workflow. Otherwise (no tool, or the lead was started without a slash command) → run the steps inline below. Workflow run: write the pm brief yourself (run-kit §3), set the STATE row, call Workflow with `name: 'technical-team:team-plan-tickets'` and `args` = `{slug, pmBrief, maxRounds, context, root}` (if the name is not found, Read `${CLAUDE_PLUGIN_ROOT}/workflows/plan-tickets.js` and pass its text as `script` with the same args). pm still writes `.team/TASKS.md`; the script checks ids, roles, files, ACs, dependencies, group order and file overlap inside a group in code, and sends violations back to pm (up to `maxRounds` pm runs, default 2). In the pm brief ask for a `milestone` and a `group` number per ticket (groups are numbered per milestone), and keep done tickets that others depend on listed, not collapsed, until the item closes. It returns `{status, rounds, tickets, milestones, issues, handoff, needsUser}`: `done` → step 4's build-loop for milestone i takes `milestones[i].groups` as `args.groups` (add one brief per ticket); `stuck` → show the `tickets` and `issues` to the user (`milestones` is empty) and decide with them; `stopped` → route `needsUser` per run-kit §5. Show the milestones and wait for OK.
4. **Build** — per milestone, on its tickets: build (`technical-team:team-developer`) → review (`technical-team:team-code-reviewer`, plus `technical-team:team-security` when feature.md step 6 says so) → test (`technical-team:team-qa`), as steps 5–7 of `${CLAUDE_PLUGIN_ROOT}/commands/feature.md`: when the **Workflow opt-in** of step 3 holds, one call of `${CLAUDE_PLUGIN_ROOT}/workflows/build-loop.js` per milestone, built as feature.md describes for its build loop (the milestone's tickets as `groups`, no `writerBrief`; README and docs stay in step 5). The milestone OK stays inline after each result; one task-list item per milestone, with the workflow's phases while it runs. Never skip review or test for a milestone. Record the milestone in STATE.md's Next step. After each milestone show what works and how to run it; wait for OK.
5. **Ship** — `technical-team:team-devops` adds CI and run/deploy files; `technical-team:team-writer` writes the README; then run `${CLAUDE_PLUGIN_ROOT}/commands/release.md` with version `0.1.0`. Its step 1 reuses the last milestone's review, security and qa reports when no code changed since; re-run only what is stale.
6. **Close** — lead §6.

Do not deploy, tag, commit or push unless the user asks; give the user the commands.
