Build this feature with the technical team:

$ARGUMENTS

You are the lead: follow `${CLAUDE_PLUGIN_ROOT}/agents/team-lead.md` §3–§6 (slug, STATE.md, TASKS.md, briefs, handoffs, closing) — Read it if you are not already the lead. Empty request → ask what to build, then stop.

`--small` is the user's flag only: it applies only when `$ARGUMENTS` contains `--small`; without it, run the full pipeline, never pick it yourself. If the request looks small (fits existing patterns: no new screen, contract or migration), you may suggest `--small` in one line at step 0 and wait for the user's yes. With `--small`: skip steps 1–5 (profile T0, no qa pre-check: the bullets are the checklist, no `qaPlanBrief`, `profile: "T0"`); write 2–5 expected-behaviour bullets into STATE.md, the developer's brief and the qa brief; exactly one ticket (one developer, `groups: [[one item]]`), no parallel groups, no ticket split by the lead.

0. **Task list** — before the first spawn, put the steps below on the session's task list, one item per step (`update_plan` in the desktop app; `TaskCreate`/`TaskUpdate` in the CLI, loaded via ToolSearch if deferred; else `TodoWrite`), and keep it current (lead §3 *Task list*).
1. **Requirements** — `technical-team:team-ba` writes `.team/requirements/<slug>.md`. Questions → show them to the user, wait, pass the answers back.
2. **Frontend design** — only with user-facing UI: `technical-team:team-designer` writes `.team/frontend-design/<slug>.md` (and `DESIGN.md` if missing).
3. **System design** — `technical-team:team-architect` writes `.team/system-design/<slug>.md`. Schema or data change → `technical-team:team-dba` fills its "Data and migrations" section. Show the user a short summary and wait for OK.
4. **Tickets** — `technical-team:team-pm` writes the item's tickets in `.team/TASKS.md`. **Workflow opt-in** — the Workflow tool is available (also if deferred) AND the user typed a slash command of this plugin for this item (this command, or `/technical-team:run`, which hands the chosen pipeline to the lead) → run the workflow. Otherwise (no tool, or the lead was started without a slash command) → run the steps inline below. Workflow run (load `technical-team:run-kit` if not loaded): call Workflow with `name: 'technical-team:team-plan-tickets'` (`${CLAUDE_PLUGIN_ROOT}/workflows/plan-tickets.js`) and `args` = `{slug, key, pmBrief, maxRounds, context, root}` (`key`: the item key from STATE.md, run-kit §3 *IDs people can read*; tickets must be `<KEY>-T<n>`). pm still writes `.team/TASKS.md`; the script checks ids, roles, files, ACs, dependencies, group order and file overlap inside a group in code, and sends violations back to pm (up to `maxRounds` pm runs, default 2). In the pm brief ask for a `group` number per ticket (no `milestone`), and keep done tickets that others depend on listed, not collapsed, until the item closes. It returns `{status, rounds, tickets, groups, issues, handoff, needsUser}`: `done` → `groups` (add one brief per ticket) is steps 5–9's `args.groups` for build-loop. Route the rest per run-kit §6 (`stuck` has an empty `groups`).
**Build loop (steps 5–9)** — **Workflow opt-in** — the Workflow tool is available (also if deferred) AND the user typed a slash command of this plugin for this item (this command, or `/technical-team:run`, which hands the chosen pipeline to the lead) → run the workflow. Otherwise (no tool, or the lead was started without a slash command) → run the steps inline below. Workflow run (load `technical-team:run-kit` if not loaded): run them as one workflow (STATE row step `5–9 (workflow)`; the user gates of steps 1–4 stay inline above) with phases `Plan`, `Build`, `Review`, `Test`, `Docs` in place of the items for steps 5–9: call Workflow with `name: 'technical-team:team-build-loop'` (`${CLAUDE_PLUGIN_ROOT}/workflows/build-loop.js`) and `args` = `{slug, groups, reviewBriefs, qaPlanBrief, qaBrief, writerBrief, state, tracker, profile, defaultProfile, scopeApproval, startAt, fromGroup, root, acceptDisputed, qaRetest, context}`.
- `groups`: the tickets of `TASKS.md` in dependency order as `[[{ticket, role, brief, files}]]`; tickets with disjoint files share a group and run in parallel. `role` is `developer`, or `dba` for migration tickets. `--small`: exactly one group with one item.
- `qaPlanBrief`: step 5 (omit with `--small`); the script runs it first, appends the pre-check line itself, and builds nothing while it is not `done` or reports a blocking spec issue (`spec-issues`). `reviewBriefs`: `{"code-reviewer": …, "security": …(only if step 7 says so), "dba": …(only with migrations)}`. `qaBrief`: step 8; the script appends the execution lines itself. `writerBrief`: only if step 9 applies. `state` (required): `{item, key, fixRounds, lastId, reviewFixes}` copied from the item's STATE.md § QA-Fix state row (first call `{item: slug, key: <KEY>, fixRounds: 0, lastId: 0, reviewFixes: 0}`; bug IDs come back as `<KEY>-B<n>`; no cap and no approvals: both are refused); `tracker` (required): the entries of `.team/reports/<slug>/findings.md` (`[]` first); both rules are run-kit §3 *QA-Fix round* and *Finding tracker*. `defaultProfile`: the task-type default (step 5); `profile`: the approved profile once known; `scopeApproval`: the lead's approval of a qa scope expansion.
- `root` (optional): the repo's absolute path, so findings with absolute paths still match a ticket's `files`.
- It returns `{status, rounds, state, cap, profile, tracker, plan, review, qa, notes, handoffs, needsUser}` (write `state` to STATE.md and `tracker` to findings.md before anything else) and runs the group check itself, so skip the lead's re-run for it. Route the result per run-kit §6; `done` → step 10.

5. **QA pre-check** — `technical-team:team-qa` with the run-kit §3 *QA briefs* pre-check line and the task-type default profile (T1, or T2 for auth, payments, migrations, data integrity): test plan, RTM per ticket and spec issues from the requirements, designs and `TASKS.md` → `.team/reports/<slug>/qa.md`. Not `done`, or a blocking spec issue → route it to ba, designer or architect (or the user), then pre-check again; no developer starts before this step passes.
6. **Build** — `technical-team:team-developer` per ticket in dependency order, each brief with the run-kit §3 developer RTM line; tickets with disjoint files may run in parallel. Migration tickets → `technical-team:team-dba`.
7. **Review** — in parallel: `technical-team:team-code-reviewer` → `.team/reports/<slug>/review.md`, and `technical-team:team-security` → `.team/reports/<slug>/security.md` if the change touches auth, user input, data access, secrets, payments or personal data. FAIL → step 6 with the finding IDs.
8. **Test** — `technical-team:team-qa` → `.team/reports/<slug>/qa.md`, with the run-kit §3 execution line and profile line: first run, then retest on every later run. FAIL → read it by run-kit §3 *Reading a qa FAIL*; valid blocking findings → step 6 (fix-round cap: run-kit §3) (or `technical-team:team-debugger` if the cause is unclear), then review again.
9. **Docs** — `technical-team:team-writer` if usage, API or operations changed.
10. **Close** — lead §6.

Do not commit or push unless the user asks.
